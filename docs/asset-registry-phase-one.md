# ทะเบียนทรัพย์สินและครุภัณฑ์ — ระยะแอปพลิเคชัน

> เอกสารประวัติระยะแรก: งานส่วนขยายได้รับการพัฒนาต่อแล้ว ดู [การเปิดใช้ส่วนขยายครุภัณฑ์](asset-extensions.md) สำหรับสถานะและขั้นตอนปัจจุบัน

## ขอบเขตตามคำสั่งผู้ใช้

พักงานฐานข้อมูลไว้ก่อน: ไม่แก้ไฟล์ SQL ไม่สร้างหรือรัน migration ไม่เชื่อมฐานข้อมูลเพื่อทดสอบ และไม่เพิ่ม query ที่ต้องใช้ column/table ใหม่ ใช้ `asset_class` และข้อมูลกลางที่มีอยู่ในโค้ดเดิมเท่านั้น การตรวจครั้งนี้ไม่ได้ยืนยัน schema ของระบบจริง

| ส่วน | พฤติกรรมเดิม / ความเสี่ยง | งานระยะนี้ | วิธีตรวจ |
| --- | --- | --- | --- |
| ฟอร์มและ import | non-IT ยังถูกบังคับข้อมูล IT; ข้อมูลที่ไม่ส่งอาจถูกล้าง | ใช้นโยบายประเภทเดียวกัน เก็บ field ที่ไม่ส่ง แยกข้อมูล IT | unit และ route/action regression |
| ทะเบียนกลาง | partial update ล้างวันที่; เปลี่ยนกลุ่มรายการที่ผูก Agent ได้ | แยก omitted/clear และป้องกันการเปลี่ยนรายการที่ยังผูก Agent | mock repository tests |
| Agent | จับคู่จากชื่อ/serial โดยไม่ตรวจกลุ่ม | ตรวจ IT Hardware และประเภทเครื่องก่อนจับคู่/เขียน/เชื่อม | inventory/link regression |
| รายการและรายละเอียด | แสดง Hardware และข้อมูลเครือข่ายใน non-IT | แสดงข้อมูลตามกลุ่ม รักษา URL/QR เดิม | typecheck, render tests |
| สถิติ | Hardware รวม non-IT; dashboard ไม่อ่าน asset_class | แยก IT Hardware, IT Software และ non-IT | mixed-class fixtures |
| import/export | ไฟล์เก่าอาจเปลี่ยนกลุ่มหรือสถานะเมื่อแก้ไข | ข้อมูลที่เว้นว่างใน import update รักษาค่าเดิม รูปแบบ export เดิม | CSV regression |

## งานที่พักไว้จนกว่าฐานข้อมูลพร้อม

- master ประเภทย่อยที่สัมพันธ์กับ asset_class และการปิดใช้งานโดยไม่ทำลายรายการเก่า
- ตารางส่วนขยายอ้างอิง information_assets.id สำหรับข้อมูล Office/Medical/Vehicle/Building/Utility/Other
- ฟอร์ม field เฉพาะประเภท การค้นหา และ import/export field เหล่านั้น
- transaction ระหว่างทะเบียนกลางและส่วนขยาย, migration, indexes, schema validation และ database integration tests

ไม่ใช้ device_type, asset_group หรือ manufacturer_specification เป็นที่ซ่อน JSON/ประเภทย่อยใหม่ ไม่แสดง field เฉพาะประเภทที่ผู้ใช้กรอกแล้วระบบยังบันทึกไม่ได้ ข้อมูลรายละเอียดทั่วไปยังบันทึกใน field เดิมได้ตามปกติ

เมื่อเริ่มระยะฐานข้อมูล ให้เลือกตารางส่วนขยายแบบหนึ่งต่อหนึ่ง มี validated JSON ที่มี schema version สำหรับรายละเอียดที่แตกต่างกัน และ FK ไปยัง master ประเภทย่อย; field ที่ต้องค้นหา/รายงานบ่อยพิจารณา typed columns และ index หลังวัด query จริง คง field IT เดิมทั้งหมด

## แผนเปิดใช้งานภายหลัง

1. ตรวจ schema จริงและ prerequisite ของ migration เดิมบนระบบทดสอบ สำรองข้อมูลและเก็บ asset ID/ความสัมพันธ์/ค่าที่สำคัญก่อนเปลี่ยน
2. เพิ่มตารางส่วนขยายและ master แบบรันซ้ำได้ ทดสอบการอ่านข้อมูลเก่าและ rollback ของแอป ห้ามถือว่า MySQL DDL rollback ด้วย transaction ได้ทั้งหมด
3. ต่อ repository ที่เขียนทะเบียนกลางและส่วนขยายใน transaction เดียว แล้วเปิดฟอร์มและรูปแบบ import/export ขยายพร้อมกัน
4. ทดสอบ Agent, สิทธิ์หน่วยงาน, โอนย้าย, ตรวจนับ, จำหน่าย, QR และข้อมูลจริงในระบบทดสอบก่อน deploy
5. หากย้อนแอปกลับ ให้เก็บ schema และข้อมูลส่วนขยายไว้ ห้าม drop ข้อมูล non-IT ที่สร้างแล้ว

ผลทดสอบของระยะนี้ยืนยันเฉพาะโค้ดและฐานข้อมูลจำลอง ไม่ใช่หลักฐานว่าฐานข้อมูลจริงพร้อมใช้งาน
